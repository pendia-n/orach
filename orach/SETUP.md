# Orach setup

## Provider keys: one per provider

One Tavily key, one Exa key and optionally one Firecrawl key. API keys authenticate usage; multiple keys within an account usually share its allowance. Do not rely on key rotation to multiply credits.

Set `TAVILY_API_KEY` and `EXA_API_KEY` on **orach**, using Wrangler's interactive secret entry or the Cloudflare dashboard. Firecrawl is a manual fallback; the automatic worker does not need its key. No provider is called on ordinary page views, budget edits or signup.

The schedule picks the top 10 searched cities over 30 days, on the 1st and 15th, 02:00 UTC. Per city it makes four Tavily Basic searches and four Exa Answer calls. For ten cities and two cycles, the nominal baseline is **80 Tavily credits and 80 Exa Answer calls** (about US$0.40 at a US$0.005 base rate, actual response cost wins). No Firecrawl calls or Agent calls. These are discovery/review drafts, not proof of full section coverage. It reserves US$0.02 per Exa call until the returned cost is recorded; failed calls keep conservative reservations. Global caps: 1,000 Tavily credits and US$10 Exa monthly. Entries and comments are never automatically rewritten by the cron. Provider quota errors stay failed; no silent paid fallback.

To inspect pending work: D1 `research_jobs` filtered by `needs_review` or `awaiting_key`. Check the source, geography, expiry, units and conditions; approved structured entries go to `city_entries` with `published=1`. The current MVP has no admin publishing screen. Do not publish entire raw responses or API credentials.

## Stripe: fiat and USDC

1. Open Stripe Dashboard. Use a separate sandbox to test. Complete business verification before live selling.
2. Enable cards/other fiat methods in Settings → Payment methods. Request/enable **Stablecoins and Crypto** if the account is eligible. An enabled integration does not guarantee Stripe approval or visibility to every buyer. Checkout uses USD and dynamic payment methods; no `payment_method_types` restriction.
3. Create a restricted server API key with Checkout Sessions write access (and any additional access Stripe requires for the configured flow). Keep it server-side. Configure it as `STRIPE_SECRET_KEY` on the **orach** worker. Do not paste credentials into chat or source files.
4. In Stripe **Workbench → Webhooks** (or Developers → Webhooks), select **Add destination → Webhook endpoint**. Choose events from your account. Use your deployed origin followed by **`/api/stripe/webhook`**.
5. Select these events:
   - `checkout.session.completed`
   - `checkout.session.async_payment_succeeded`
   - `checkout.session.async_payment_failed`
   - `charge.refunded`
6. Save the endpoint. Open it, reveal its **Signing secret** (`whsec_...`), and enter it directly into Cloudflare as `STRIPE_WEBHOOK_SECRET`. The signing secret is generated by Stripe for that endpoint; it is different from your API key. Sandbox and live endpoints have different signing secrets.
7. Configure `ORACH_PUBLIC_ORIGIN` as the deployed HTTPS origin (no trailing slash), and `ORACH_PASS_PRICE_CENTS` as `799`. Set the origin and price as non-secret variables or secrets. Both API and webhook keys must be configured before checkout activates. Never configure live credentials before verifying refunds, required seller information and tax obligations.
8. Make a sandbox purchase. Confirm the pass remains inactive for an unpaid completed session, activates only on a valid paid webhook, is not duplicated by repeated events and is revoked on a full refund. Validate the actual USDC payment separately if available. A success redirect alone never grants access.

### Local webhook testing

Use Stripe CLI `stripe listen --forward-to http://localhost:5173/api/stripe/webhook` with your sandbox. Enter the CLI-provided signing secret into ignored `.dev.vars` as `STRIPE_WEBHOOK_SECRET`, and the matching sandbox API key as `STRIPE_SECRET_KEY`. Do not use the Dashboard endpoint secret for the CLI listener. Restart local development after changing local variables. Local `Secure` cookies work on localhost in supporting browsers; production must use HTTPS.

### Secret entry

Use Cloudflare Dashboard → Workers & Pages → orach → Settings → Variables and Secrets, or interactive `pnpm exec wrangler secret put VARIABLE_NAME`. All app and research credentials go on this one worker. Never print credential values. The generated `ORACH_JWT_SECRET` is already stored in root `.env`; preserve it across deployments. Rotating it signs out users.

## Deployment

`pnpm check` then `pnpm build`, deploy the single app-and-scheduler worker with `pnpm exec wrangler deploy`. Apply migrations before deploying handlers that need them. No commit or push is needed.
